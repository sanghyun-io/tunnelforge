# Export/Import 점검 보고 (v2.17.1, bb3c53b, 읽기 전용)

## 1. 한 줄 결론

사용자 규칙(덤프에 있는 테이블은 덮어쓰고, 없는 테이블은 만들고, 덤프 밖 테이블은 건드리지 않기)을 지키는 모드는 '고급: 전체 교체' 하나뿐입니다. '완전 재생성'은 이 모드와 똑같습니다. 전체 교체도 중간에 실패하면 앞서 교체한 테이블에 인덱스와 FK가 빠진 채 남아서 "피해는 그 테이블 하나"라는 기준을 지키지 못합니다. 기본값인 안전 복원과 덮어쓰기는 규칙과 다르게 동작하고, DB 범위 계정에서는 아예 실패합니다.

검증 범위: MySQL 8.0.46·8.4.11은 실제 코어로 계정 7종을 만들어 확인했습니다. PostgreSQL은 코드만 읽었습니다.

## 3. 확인된 버그

표시 기준은 다음과 같습니다.
- **검증됨**: 반박을 시도하는 검증을 통과한 항목
- **실측**: 실제 DB에서 재현한 항목
- **미검증**: 위 검증을 거치지 않은 항목

검증 과정에서 버그가 아니라 설계 문제로 재분류된 두 건(트리거 삭제, 안전 복원 실패 문구)은 4장으로 옮겼습니다.

### 높음

**B1. 권한이 좁은 계정으로 Export하면 트리거·루틴·이벤트가 빠지는데도 '완전한 덤프'로 표시됩니다.** 검증됨, 실측.
- 근거: 이 객체들은 권한에 따라 걸러지는 information_schema로만 찾습니다 (schema.rs:449-471). 거부 여부도 그 목록만 보고 정합니다 (dump.rs:838-855). 그래서 `strict_export`가 true로 남습니다 (dump.rs:764-775). Import도 경고하지 않습니다 (import.rs:106-122). 정책 문서는 "트리거는 Export 전에 거부"라고 적어 놓았습니다 (docs/export_import_policy.md:235).
- 실측: `SELECT, LOCK TABLES ON db.*` 계정으로는 트리거·루틴·이벤트가 0/0/0으로 보였습니다 (root는 1/1/1). 결과는 거부 없이 `strict_export=true`였습니다. 테이블 단위로 SELECT만 받은 계정은 테이블 자체가 빠졌는데도 '완전'으로 표시됐습니다.
- 시나리오: 읽기 전용 계정으로 운영 DB를 전체 백업합니다. 프로시저와 트리거가 빠진 백업을 완전한 백업이라고 믿게 됩니다.
- PG: 트리거가 같은 방식(schema.rs:676-683)이라 같은 문제가 있을 가능성이 높지만 미검증입니다.

### 중간

**B2. REFERENCES 권한이 없는 앱 계정으로 전체 교체를 하면, 모든 테이블을 교체한 뒤에야 FK 단계에서 실패합니다.** 검증됨, 실측.
- 근거: 사전 점검은 FK가 없는 CREATE만 시험합니다 (import.rs:517-537). FK는 모든 적재가 끝난 뒤에 붙입니다 (import.rs:883 → ddl.rs:263-303).
- 시나리오: ERROR 1142로 실패하면 대상 전체에 FK가 없고, 뷰도 만들어지지 않습니다. 행 데이터는 모두 들어가 있습니다.

**B3. DB 범위 계정은 legacy ENUM 빈값('')이 많은 테이블을 Import하지 못하고, 그 테이블은 빈 채로 남습니다.** 검증됨, 실측.
- 근거: v2.17.1부터 경고 상한이 1024로 남습니다 (adapters.rs:789-799). 그런데 배치 크기와 분할 기준은 여전히 65535를 전제로 잡혀 있습니다 (import.rs:24, 1825, 1878-1881). 경고 수가 실제 경고 행 수와 다르면 거부합니다 (import.rs:1919-1921, 1949-1956).
- 시나리오: ENUM 3열 × 600행을 넣으면 "1500 MySQL warnings"로 실패하고 테이블은 0행입니다. root로 넣으면 성공합니다. 조건은 열 개수가 아니라 "한 문장에 '' 칸이 1024개를 넘는지"입니다.

**B4. FK 자동 포함을 끄고 부분 Export하면, 덤프 밖 테이블을 가리키는 FK를 사전에 점검하지 않습니다.** 검증됨.
- 근거: 대상 쪽에서 들어오는 FK만 점검합니다 (dump_format.rs:524-528, 772-775, import.rs:694-708). 덤프 밖으로 나가는 FK는 마지막에 처음 생성됩니다 (ddl.rs:186-214).
- 시나리오: orders만 내보내서 교체합니다. 대상 users.id와 타입이 다르면(3780) 또는 PG면, 모든 테이블을 교체한 뒤에 실패합니다.
- 참고: MySQL이 고아 행을 받아 주는 것은 mysqldump와 같은 동작이므로 버그가 아닙니다.

**B5. 데이터 추가가 대상에 없던 테이블을 새로 만들 때 보조 인덱스와 FK를 만들지 않는데, 결과는 성공으로 표시합니다.** 검증됨.
- 근거: import.rs:427-431, ddl.rs:1271-1303. 후처리는 replace/recreate에서만 돌고 (ddl.rs:255-257), merge에서는 "기존 객체가 이미 맞을 것"이라며 건너뜁니다 (import.rs:875-892). PG는 UNIQUE와 주석도 빠집니다.
- 시나리오: 새 테이블 orders에 customer_id 인덱스도 FK도 없습니다. 아무 경고도 없습니다.

**B6. PG에서 데이터 추가를 하면 시퀀스(identity)를 다시 맞추지 않습니다.** 검증됨.
- 근거: 시퀀스 재설정은 후처리에만 들어 있습니다 (ddl.rs:233-273). merge는 후처리를 호출하지 않습니다 (import.rs:875).
- 시나리오: 기존 테이블의 시퀀스가 100에 있는데 id 500까지 추가하면, 앱의 다음 INSERT가 101~500에서 중복 키로 실패합니다. 새로 만든 테이블은 1에서 바로 충돌합니다.

**B7. MySQL에서 데이터 추가를 할 때 대상에 같은 뷰가 이미 있으면 'Import 실패'로 표시됩니다.** 검증됨, 실측.
- 근거: 뷰를 지우는 건 replace/recreate뿐입니다 (import.rs:1036-1042). MySQL 뷰 정의는 OR REPLACE 없는 일반 CREATE VIEW입니다 (schema.rs:792-800). 그래서 1050 오류가 나고 `success=false`가 됩니다 (import.rs:913-916, rust_dump_exporter.py:685).
- 시나리오: 행은 이미 다 들어갔는데 화면은 실패라고 합니다. 정책상 merge를 다시 실행하면 안 되므로 사용자는 어떻게 해야 할지 판단할 수 없습니다.

**B8. 보고서 파일 하나를 계속 덮어써서 이전 시도의 손상 기록과 백업 추적이 사라집니다.** 검증됨.
- 근거: 경로가 하나로 고정돼 있습니다 (dump_format.rs:852-857). 시도할 때마다 맨 먼저 덮어씁니다 (import.rs:199-200, safe_restore.rs:168). 작업 기록도 모두 같은 파일을 가리킵니다 (job_recording.py:97, 119-120). 최신 보고서 하나만 백업으로 등록합니다 (safe_backups.rs:82-98).
- 시나리오: 교체에 실패해서 "orders 삭제 후 미복원"이 기록됐습니다. 다시 실행했는데 사전 점검에서 실패하면 그 기록이 사라집니다. 같은 폴더로 덮어쓰기를 두 번 하면 첫 `tf_backup_*`은 '소유 증명 안 됨'으로 바뀌어 정리도 되돌리기도 할 수 없습니다.

**B9. 데이터 추가가 실패한 뒤 '같은 설정으로 다시 Import'를 누르면 키 없는 테이블에 행이 조용히 중복됩니다.** 검증됨. 코어 버그가 아니라 화면이 정책과 어긋나는 문제입니다.
- 근거: 모드와 상관없이 버튼이 나옵니다 (db_import_dialog.py:790-793, 1638-1650). merge에는 확인창이 없습니다 (1217-1234). 정책 문서에는 "명시적 확인, merge를 그대로 반복하지 말 것"이라고 되어 있습니다 (export_import_policy.md:153-157).
- 시나리오: PK가 없는 로그 테이블에 같은 행이 한 번 더 들어갑니다. 키가 있는 첫 테이블을 만나면 거기서 멈춥니다.

### 낮음 (미검증)

**B10. DROP 도중 연결이 끊겨 삭제 여부를 알 수 없는 테이블이 실패창 어디에도 나오지 않습니다.**
- 근거: import.rs:625-632, 153-154 / db_import_dialog.py:68, 95-114

**B11. 사전 점검용 `tf_probe_*` 테이블이 중지하거나 DROP에 실패하면 대상 DB에 남습니다.**
- 근거: import.rs:517-550

**B12. 대상에 덤프 테이블과 같은 이름의 VIEW가 있으면 사전 점검을 통과한 뒤 중간에서 실패합니다.**
- 근거: import.rs:609-611, 670-680

**B13. RELOAD만 있고 BACKUP_ADMIN이 없는 계정은, Export 때 서버 전체 읽기 잠금을 잡은 뒤에야 실패합니다.**
- 근거: dump.rs:160-191
- 상태: 실측은 했지만 반박 검증은 거치지 않았습니다.

## 4. 규칙과 어긋나는 설계와 헷갈리는 화면 (우선순위 순)

### 규칙과 어긋나는 설계

1. **교체가 중간에 실패하면 이미 교체된 테이블에 인덱스와 FK가 없는데, 화면은 성공으로 표시합니다.**
   - 원인: 보조 인덱스와 FK(PG는 UNIQUE와 시퀀스까지)를 모든 테이블을 끝낸 뒤 한꺼번에 만듭니다 (import.rs:486-515, ddl.rs:157, 263-303, 1271-1303).
   - 화면 안내(db_import_dialog.py:675-679), 실패 상세(95-114), 정책 문서(:36) 모두 "진행 중이던 테이블만 문제"라고만 설명합니다.
   - 예: 10개 중 7번째에서 실패하면 1~6번은 인덱스와 FK가 없습니다. 복구 방법은 전체를 다시 실행하는 것뿐입니다.
2. **기본값인 안전 복원은 규칙 1·2를 적용하지 않습니다.** 대상 DB가 있으면 복사본에만 넣고 검토창으로 넘어갑니다 (safe_restore.rs:330-341, 420-427 / db_import_dialog.py:646-648).
3. **MySQL 덮어쓰기는 FK나 뷰로 엮인 대상 전용 테이블을 SHOW CREATE 텍스트로 다시 만들어 교체합니다** (TF-STATUS-173).
   - 원본 테이블은 `tf_backup_*`로 옮겨집니다.
   - 엮이지 않은 테이블은 그대로 둡니다. PG는 규칙을 지킵니다 (safe_promote_postgres.rs:142, 417-426).
4. **안전 복원과 덮어쓰기는 흔한 대상에서 성립하지 않습니다.** 다음 중 하나라도 해당하면 막힙니다.
   - CREATE DATABASE 권한이 없을 때 (safe_restore.rs:497-505)
   - 전역 SELECT/SHOW VIEW/PROCESS 권한이 없을 때 (safe_promote_mysql.rs:121-127)
   - 루틴이나 이벤트가 하나라도 있을 때 (896-911)
   - 대상 테이블에 트리거가 있을 때 (300-310)
   - PG에 GRANT, 루틴, 트리거가 있을 때 (safe_promote_postgres.rs:187-222)
   - 원본 데이터에 FK 고아 행이 있을 때 (safe_restore.rs:609-637). 같은 덤프를 replace는 받아 줍니다.
   - 부분 덤프면 대상 전용 테이블이 생기므로 항상 검토창으로 갑니다 (safe_restore.rs:287-305, db_import_dialog.py:1915-1925).
5. **FK 자동 포함이 기본으로 켜져 있고, 추가된 테이블이 어디에도 보이지 않습니다.** 그래서 교체가 사용자가 고르지 않은 부모 테이블까지 덮어씁니다. 오늘 겪은 사례입니다.
   - 근거: db_export_dialog.py:526-527, rust_dump_exporter.py:432-440. 추가 목록은 `_export_metadata.json`에만 기록되고(457, 483) 아무 데서도 읽지 않습니다.
6. **트리거가 사라집니다 (검증 후 설계 문제로 재분류).** 두 경우가 있습니다.
   - 불완전 Export로 트리거가 빠진 덤프로 교체할 때
   - 대상에만 트리거가 있는 테이블을 교체할 때. DROP TABLE이 트리거도 함께 지웁니다 (dump.rs:824-853, import.rs:600-637, ddl.rs:1943).
   - 결과 메시지에 "source dump: Object not exported" 한 줄만 남습니다 (import.rs:107-109). 확인창에는 아무것도 없습니다. mysqldump는 트리거를 다시 만듭니다.
7. **Export가 거부하는데 사용자가 해제할 수도 없는 정의가 있습니다.** FULLTEXT, generated column, 함수식/DESC 인덱스, 식 기본값, 안전하지 않은 CHECK, 다른 DB를 참조하는 FK입니다 (dump.rs:813, 838-855 / schema.rs:478-485, 495). 이런 테이블은 복사할 방법이 없습니다. mysqldump로는 됩니다.
8. **PG 교체는 덤프에 들어 있는 뷰라도 의존 뷰가 있거나, 대상 전용 FK 자식이 있으면 통째로 거부합니다** (import.rs:683-708, live_import_policy.rs:643-661). 그래서 PG를 매일 새로 받으면 두 번째부터 실패합니다.
9. **MyISAM/MEMORY 테이블은 불완전 Export를 고르면 테이블째 빠지고, 대상에는 예전 데이터가 남습니다** (dump.rs:860-875, 1022-1055).
10. **MySQL 파티션을 감지하지 않습니다.** 교체하면 일반 테이블로 바뀝니다 (policy.md:251-252).
11. **세부 정보가 빠집니다.**
    - 인덱스 주석과 ROW_FORMAT (adapters.rs:72-139)
    - 뷰가 DEFINER에서 호출자 권한(INVOKER)으로 바뀜 (schema.rs:839-850)
12. **교체 대상 DB가 없으면 만들지 않고 'Unknown database'로 실패합니다** (import.rs:348, adapters.rs:811). 미검증입니다.

### 헷갈리는 화면

1. **모드가 5개입니다.**
   - 두 모드가 'mysqldump처럼'이라고 설명합니다 (db_import_dialog.py:656, 674-677).
   - '완전 재생성'은 전체 교체와 완전히 같습니다 (687-693).
   - 규칙대로 동작하는 유일한 모드에 '고급' 표시와 주황색이 붙고, 확인창은 "안전 복원 대신 직접 변경하시겠습니까?"라고 묻습니다 (673-680, 1218-1221).
   - 위험한 데이터 추가에는 확인창이 없습니다 (1217-1234).
2. **확인창에 덮어쓸 테이블, 새로 만들 테이블, 건드리지 않을 테이블 목록이 없습니다.**
   - 고를 수 없는데도 '선택한 테이블'이라고 씁니다 (673-676, 1217-1225).
   - 덤프의 주의사항(불완전, 시점 불일치, 부분 덤프, 자동 추가된 테이블)도 시작 전에 보이지 않습니다 (rust_dump_exporter.py:524-565). 덤프 정보 파일(manifest)에는 범위를 나타내는 필드조차 없습니다 (adapters.rs:242-267).
3. **안전 복원 실패 원인을 버리고 일반 문구로 바꿔 보여 줍니다.** 검증됨.
   - 근거: rust_dump_exporter.py:645-653 → db_import_dialog.py:1765-1766
   - 예: 오늘 같은 DB 범위 계정으로 기본 Import를 하면 "검증된 새 대상 정보를 확인할 수 없습니다"만 보이고, 실제 원인인 Access denied는 보이지 않습니다.
4. **실패나 중지 화면이 피해를 정확히 알려 주지 않습니다.**
   - 실패한 테이블이 있으면 원인 문구를 아예 뺍니다 (1769-1777).
   - 후처리가 실패하면 모든 테이블을 성공으로 표시하고 다시 실행 버튼도 숨깁니다 (1642-1650).
   - 중지했을 때 삭제된 테이블을 보여 주지 않습니다 (1762-1763).
   - 대상을 건드리지도 않은 검증 실패에도 '실패, 다시 실행'을 띄웁니다 (rust_dump_exporter.py:491-514).
5. **덮어쓰기 검토창이 다시 만들어질 테이블을 '(유지)'로 표시합니다** (db_import_dialog.py:132, safe_promote_mysql.rs:859).
6. **쓰고 남은 DB가 쌓입니다.**
   - 실패한 복사본 `tf_restore_*`는 도구로 지울 수 없습니다 (safe_backups.rs:406-422).
   - 없는 이름으로 복원하다 실패하면 그 이름으로 부분 DB가 남고, 다음 실행에서는 이것을 '원본'으로 취급합니다 (safe_restore.rs:330-352, 441-451).
   - 성공해도 `tf_promote_*`, `tf_backup_*`, 별칭 뷰 `tf_p_*_oldv*`가 남습니다 (safe_promote_mysql.rs:1141-1147, 1297-1300).
7. **원문이 그대로 노출됩니다.** 코어의 영문 오류 원문이 그대로 나오고, 전환 완료 창은 결과 JSON을 그대로 보여 줍니다 (db_export_dialog.py:1434 / db_import_dialog.py:1776, 1892).
8. **Import 화면의 작은 문제들**
   - '원본 스키마명 사용'을 켜면 회색 콤보가 실제 대상과 상관없는 DB를 보여 줍니다 (899-905, 1138-1146).
   - 고른 모드를 기억하지 않아 매번 안전 복원으로 돌아갑니다 (647).
   - 환경이 미분류이면 같은 질문을 두 번 받습니다 (production_guard.py:366-383).
9. **Export 화면**
   - 테이블 목록에 체크와 파란 선택이 함께 있어서 헷갈립니다 (db_export_dialog.py:520, 961, 993-999).
   - 범위 밖 객체까지 'Object not exported' 경고를 붙이고 strict를 해제합니다 (dump.rs:897-900).
   - 연결 수 제한이 있는 계정은 1226 원문 오류로 실패하고 대안 안내가 없습니다 (dump.rs:113-121).
   - 중지 버튼이 없습니다.
10. **소소한 것**
    - 호환성 패널이 대상 버전과 상관없이 빨간 오류를 표시합니다 (989-1009).
    - 덮어쓰기 로그에 '안전 복원'이라고 기록됩니다 (1244, 1292).
    - 정책 문서는 SPATIAL을 거부한다고 하지만 코드는 지원합니다 (policy.md:234, schema.rs:495).
    - '같은 설정으로 다시 Import'는 실제로는 현재 화면 값으로 실행합니다 (793). 부분 재시도 코드는 쓰이지 않습니다 (1988-1993).

## 5. 권한 요구사항

MySQL은 실측했고, PostgreSQL은 코드만 읽었습니다.

| 작업 | 필요한 권한 | 없을 때 | 판정 |
|---|---|---|---|
| Export 기본 (병렬, 같은 시점) | 전역 RELOAD(또는 FLUSH_TABLES) + BACKUP_ADMIN + SELECT | 확인창이 뜨고 테이블 잠금 방식으로 넘어감 | 안전하게 대체. 단 RELOAD만 있으면 잠금을 먼저 잡은 뒤 실패 (B13) |
| Export 테이블 잠금 병렬 | 해당 DB의 SELECT + LOCK TABLES | 두 번째 확인창: 단일 연결(같은 보장) 또는 병렬(시점 보장 없음) | 안전하게 대체 |
| Export 단일 연결, 비동기 병렬 | SELECT | 없음 | 동작 |
| 뷰 정의 수집 | SHOW VIEW | 경고를 남기고 불완전으로 표시 | 안전하게 강등 |
| 트리거·루틴·이벤트 확인 | TRIGGER / SHOW_ROUTINE·EXECUTE·전역 SELECT 중 하나 / EVENT | 보이지 않아서 '완전'으로 표시됨 | 조용한 누락 (B1) |
| 테이블 목록 | 테이블별 SELECT | 안 보이는 테이블이 빠진 채 '완전'으로 표시됨 | 조용한 누락 (B1) |
| 동시 연결 | max_user_connections가 스레드 수+2 이상 | 1226 원문 오류 | 실패 |
| Import 교체·추가 | 해당 DB의 SELECT, INSERT, CREATE, DROP, ALTER, INDEX | 없음 | 동작 (DB 범위 계정으로 실측) |
| FK 생성 | REFERENCES | 모든 테이블을 교체한 뒤 실패 | 늦게 실패 (B2) |
| 뷰 생성 | CREATE VIEW | 뷰만 실패하지만 결과는 '실패'로 표시 | 부분 실패 |
| 경고 상한 올리기 | SESSION_VARIABLES_ADMIN | 1024 그대로 진행 (v2.17.1) | 안전하게 대체. 단 ENUM '' 대량은 실패 (B3) |
| LOAD DATA 임시 허용 | SUPER 또는 SYSTEM_VARIABLES_ADMIN | INSERT 방식으로 바꿔서 진행 | 안전하게 대체 |
| 대상 DB가 없을 때 (교체·추가) | CREATE (서버 단위) | DB를 만들지 않고 'Unknown database' | 실패 (미검증) |
| 안전 복원 (기본) | 위 권한 + `tf_restore_%` DB 생성 | 1044, 원본은 그대로, 원인은 일반 문구로 가려짐 | 실패 |
| 덮어쓰기 교체 | 위 권한 + 전역 SELECT/SHOW VIEW/PROCESS + `tf_backup_%`·`tf_promote_%` 생성 | 교체 차단, 버튼 비활성 | 실패 |
| PG 덮어쓰기 | 소유자 일치, 스키마에 GRANT·루틴·트리거·룰이 없을 것 | 교체 차단 | 실패 |

DB 범위 계정으로 실제 동작하는 모드는 교체, 재생성, 데이터 추가 세 가지뿐입니다. 사용자 규칙을 지키는 기본 동작은 권한 면에서도 가장 덜 까다롭습니다.

## 6. 설계안: 기본 동작 하나와 서로 독립적인 고급 옵션

### 6-1. Import

**기본 동작 (아무것도 바꾸지 않으면 이대로 실행)**
1. 덤프의 원래 DB 이름으로 넣습니다. 이름은 화면에 표시합니다. 그 DB가 없으면 만듭니다.
2. 덤프의 테이블마다 처리합니다.
   - 대상에 있으면: 지우고 → 덤프 구조로 만들고 → 적재하고 → 그 테이블의 인덱스와 FK까지 마무리합니다.
   - 대상에 없으면: 만들고 적재합니다.
   - 덤프에 없는 테이블은 건드리지 않습니다.
3. 첫 오류에서 멈춥니다. 피해는 그 테이블 하나이고, 나머지 테이블은 원래 상태입니다.
4. 시작 전에 확인창을 **딱 한 번** 띄웁니다.
   - 덮어쓸 N개, 새로 만들 M개, 건드리지 않을 K개 (이름은 펼쳐서 볼 수 있음)
   - 덤프 주의사항: 빠진 객체, 시점 불일치, 자동으로 포함된 부모 테이블, 대상에서 사라질 트리거
   - 운영 환경이면 이 창에서 DB 이름을 입력받습니다.
5. 타임존은 덤프에 기록된 값을 쓰고, 동시 작업은 8개입니다. 고른 값은 다음에도 기억합니다.

**고급 (펼쳐야 보이는 독립 옵션)**

| 옵션 | 기본값 | 켜면 | 코어 매핑 | 사라지는 것 |
|---|---|---|---|---|
| 다른 DB 이름으로 넣기 | 끔 (덤프 원래 이름) | 이름을 입력. 없는 이름이면 새 DB를 만들어 넣음. 원본을 건드리지 않고 따로 받아 보는 용도 = 지금의 '안전 복원' | `target` 이름. 없는 DB를 만드는 기능을 코어에 추가 (지금은 safe에만 있음) | '원본 스키마명 사용' 체크박스, 회색 콤보, '안전 복원' 라디오 |
| 먼저 복사본에서 검증하고 교체 | 끔 | 복사본 DB에 넣고 검증한 뒤 덤프 테이블만 한 번에 교체. 이전 테이블은 백업 DB에 보관. 권한이 없거나, 루틴이 있거나, 규칙 3을 지킬 수 없으면 **적재 전에** 이유를 보여 주고 멈춤 | `mode=safe` + `dump.promote` | '덮어쓰기' 라디오, '덮어쓰기 확인' 창, '안전 복원 검증 완료' 창 |
| 지우지 말고 행만 덧붙이기 | 끔 | 기존 테이블 구조를 유지하고 행만 추가. 없는 테이블은 만듦. 실패 후 '다시 실행' 버튼 없음 | `mode=merge` | '데이터 추가 Import' 라디오 |
| 타임존 직접 정하기 | 끔 (덤프 기록값) | KST / UTC / 서버 기본값 중 선택 | `use_source_timezone=false` + `timezone_sql` | 4개짜리 타임존 라디오 묶음 |
| 동시 작업 수 | 8 | 1~16 | `threads` | 없음 (고급 영역으로 옮김) |

- 기본 동작은 `mode=replace`입니다. '고급:' 표시와 주황 경고를 없앱니다. '완전 재생성' 라디오는 지우고, 코어의 `recreate` 별칭은 이전 기록과 호환되도록 남깁니다.
- 함께 쓸 수 없는 조합은 하나뿐입니다. '복사본에서 검증'과 '행만 덧붙이기'는 코어에 해당 경로가 없으므로, 하나를 켜면 다른 하나를 회색으로 바꾸고 이유를 한 줄로 보여 줍니다.

### 6-2. Export

**기본 동작**
1. 전체 DB를 내보냅니다. '테이블 고르기'를 고르면 체크박스로만 선택합니다.
2. 계정 권한을 **먼저 확인한 뒤** 같은 시점을 보장하는 방법 중 가장 빠른 것을 자동으로 고릅니다.
   - 전역 잠금 권한이 있으면 전역 잠금 스냅샷
   - 없으면 테이블 잠금 스냅샷
   - 그것도 없으면 단일 연결
   - 어떤 방법을 썼는지는 로그와 완료창에 한 줄로 알려 줍니다.
   - 연결 수 제한이 있으면 동시 작업 수를 낮춥니다.
3. 권한 때문에 트리거·루틴·이벤트를 다 볼 수 있다는 걸 증명하지 못하면 결과를 '불완전'으로 표시하고 경고합니다 (B1 해결).
4. 고른 테이블이 덤프 밖 테이블을 FK로 가리키면 목록 아래에 한 줄로 알려 줍니다. 별도 창은 띄우지 않습니다.
5. 담을 수 없는 객체가 있으면 파일을 쓰기 전에 멈추고, 테이블 이름과 이유를 사람이 읽을 수 있는 문장으로 보여 줍니다.

**고급**

| 옵션 | 기본값 | 켜면 | 코어 매핑 | 사라지는 것 |
|---|---|---|---|---|
| 연결된 부모 테이블 함께 담기 | **끔** | 고른 테이블이 FK로 가리키는 부모를 추가함. 추가된 테이블은 시작 전에 목록에 체크된 상태로 보임 | `include_fk_parents` | 지금의 '기본 켜짐 + 몰래 추가' |
| 시점 일관성 포기하고 빠르게 | 끔 | 단일 연결로 떨어질 상황에서 워커마다 따로 스냅샷을 씀. 덤프에 '시점 불일치'로 기록 | `mysql_snapshot_mode=parallel_unsynchronized` | 권한 확인창의 '병렬로 계속' 버튼 |
| 담을 수 없는 객체는 빼고 내보내기 | 끔 | 확인창 없이 빼고 진행. 결과는 '불완전'으로 표시 | `allow_incomplete=true` | 없음 (꺼져 있을 때만 확인창이 뜸) |
| 동시 작업 수 / 압축 | 8 / zstd | 직접 지정 | `threads` / `compression` | 없음 |
| 폴더 이름 직접 정하기 | 끔 (이름+DB+시각) | 직접 입력 | Python에서 이름 생성 | 자동 지정 체크박스 3개 |

### 6-3. 실행 중 확인창 정리

| 지금 뜨는 창 | 설계안에서 |
|---|---|
| Export 권한 1차 (전역 잠금 없음) | 없앰. 같은 보장인 테이블 잠금으로 자동 전환하고 안내 |
| Export 권한 2차 (LOCK TABLES도 없음) | 없앰. 단일 연결로 자동 전환. 시점 보장 없는 병렬은 토글로 |
| 불완전 Export | **남김.** 객체가 빠지는 건 사용자가 정할 일이기 때문. 토글을 켜 두면 뜨지 않음. 해제할 수 없는 거부는 "이 테이블을 빼면 진행 가능"이라고 안내 |
| Import 환경 확인 + 기존 대상 삭제 확인 + 덮어쓰기 확인 | 시작 전 확인창 하나로 합침 (운영 환경은 이름 입력 유지) |
| 안전 복원 검증 완료, 비교·전환 4버튼 창 | '복사본에서 검증'을 켰고 자동 교체로는 규칙을 지킬 수 없을 때만 띄움 |
| 전환 완료 (JSON) | 한 줄 문장으로 바꿈 (백업 이름 포함) |

### 6-4. 9/28 이후 만든 안전장치는 어떻게 되나

|---|---|

### 6-5. 구현 순서

각 단계 끝에 docs/export_import_policy.md와 docs/current_status.md도 갱신합니다.

1. **코어: 교체를 테이블 단위로 완결**
   - 변경: 테이블을 적재한 직후 그 테이블의 보조 인덱스를 만듭니다 (PG는 UNIQUE, 주석, 시퀀스까지). FK는 양쪽 테이블이 끝나는 시점에 바로 붙이고, 마지막에는 남은 FK와 뷰만 처리합니다. merge가 새로 만든 테이블도 같은 길을 타므로 B5·B6이 함께 해결됩니다.
   - 테스트: k번째 테이블에서 일부러 실패시키고, 1..k-1 테이블에 인덱스와 FK가 있는지 확인하는 MySQL/PG 라이브 테스트. 지금 코드에서는 실패해야 합니다.
2. **코어: 첫 DROP 전 점검 보강**
   - 변경: FK 시험 쌍으로 REFERENCES 권한 확인 (B2), 덤프 밖으로 나가는 FK 호환성 (B4), 같은 이름의 뷰 (B12), `@@max_error_count`를 읽어 배치 크기 계산 (B3), 대상 트리거 목록 보고.
   - 테스트: REFERENCES가 없는 계정은 아무것도 지우지 않은 채 거부되는지. DB 범위 계정으로 ENUM '' 1025칸 이상이 성공하는지.
3. **코어: `dump.import`에 `dry_run` 추가, 없는 DB는 생성**
   - 변경: 덮어쓸/새로 만들/건드리지 않을 테이블, 사라질 트리거, 덤프 주의사항을 미리 돌려줍니다. 대상 DB가 없으면 만듭니다.
   - 테스트: dry_run 뒤에 대상이 바뀌지 않았는지. 없는 이름으로 교체가 성공하는지.
4. **Import 화면 전환**
   - 변경: 라디오 5개를 기본 동작 + 토글 5개로 바꿉니다. 확인창은 하나로 합칩니다. 토글 값을 저장합니다. 실패창에 첫 원인을 보여 줍니다. 안전 복원 실패 메시지를 그대로 전달합니다 (rust_dump_exporter.py:653). merge에서는 다시 실행 버튼을 숨깁니다. JSON 창은 문장으로 바꿉니다.
   - 테스트(pytest): 기본 요청이 `mode=replace`인지, 토글별 요청 내용, recreate 라디오가 없는지, merge 실패 후 다시 실행 버튼이 없는지.
5. **보고서를 시도마다 별도 파일로 (B8)**
   - 변경: 작업 기록은 자기 보고서를 가리키고, 백업 목록은 모든 계획 디렉터리를 훑습니다.
   - 테스트: 같은 폴더로 두 번 실행하면 보고서가 두 개 남고, 첫 백업을 정리할 수 있는지.
6. **Export 코어와 화면**
   - 변경: 권한을 먼저 확인해 스냅샷 방식을 자동으로 고릅니다 (B13 해결). 연결 수 제한에 대응합니다. 가시성을 증명하지 못하면 불완전으로 표시합니다 (B1). 범위 밖 객체 경고를 뺍니다. 거부 문구를 테이블별 문장으로 바꿉니다. 권한 확인창 2개를 없애고, FK 자동 포함을 기본으로 끄고 추가된 테이블을 보여 주며, 목록은 체크박스만 남깁니다.
   - 테스트: TRIGGER 권한이 없는 계정으로 트리거가 있는 DB를 내보내면 strict=false가 나오거나 거부되는지. 지금 코드에서는 실패해야 합니다.
7. **'복사본에서 검증' 토글 정리**
   - 변경: 권한, 루틴, 대상 전용 FK 연결을 복사본에 적재하기 전에 점검합니다. 규칙 3을 지킬 수 없으면 테이블을 다시 만들지 않고 멈춘 뒤 이유를 보여 줍니다 (TF-STATUS-173 해소). 성공 후 남는 DB와 별칭 뷰, 실패한 복사본을 정리할 경로를 만듭니다.
   - 테스트: 연결되지 않은 대상 전용 테이블이 같은 테이블 그대로(다시 만들지 않고) 남는지.
8. **데이터 추가: 이미 있는 뷰는 건너뛰고 '이미 있음'으로 보고 (B7)**
   - 아래 결정 2에서 '삭제'로 정하면 이 단계 대신 기능을 지웁니다.
