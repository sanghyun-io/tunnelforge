# TunnelForge 다음 AI Agent 실행 인계서

작성 기준: 2026-09-29. 이 문서는 다음 세션의 실행 안내다. 최신 사실과 이슈 상태의 권위 있는 원본은 `docs/current_status.md`이며, 작업 시작 시 반드시 다시 읽는다. 이 문서의 과거 배포·실험 기록을 현재 소스의 새 검증 결과로 해석하지 않는다.

## 1. 목적과 확정된 결정

- 첫 사용 대상은 **개발자와 소규모 팀의 일상 DB 작업**이다. 즉시 지원 범위는 **MySQL/PostgreSQL, Windows/macOS/Linux**다. 실제 Mac 기기 및 공급자 환경의 검증은 남아 있다.
- DB 작업의 소유자는 Rust `tunnelforge-core`다. Python/PyQt는 UI, 오케스트레이션, 신호, 대화상자에 집중한다. 직접 Python DB 드라이버 핫패스, 외부 덤프 도구, 은퇴한 별칭을 다시 넣지 않는다. 패키지에는 단일 Rust Core 바이너리를 포함한다.
- Export/Import 기본값은 **안전 복원**이다. 같은 엔진의 전체 덤프를 별도 후보 네임스페이스에 준비·검증한다. 대상이 없으면 원래 이름 또는 사용자가 명시한 이름으로 배타적으로 생성한다. 대상이 있으면 먼저 별도 후보를 준비하고 기존 객체와 비교한 뒤 원본 유지, 후보 사용, 명시적으로 확인한 교체 중 선택하게 한다. PostgreSQL에서는 선택한 데이터베이스 안의 스키마를 대상으로 한다.
- 알 수 없는 전환 결과는 저널과 실제 객체를 대조하기 전 재시도하지 않는다. 후보 검증에 실패하면 원본을 유지한다. `replace`/`recreate`/`merge` 고급 모드의 비원자성도 숨기지 않는다.
- macOS는 GitHub Releases 직접 배포의 **unsigned arm64/x86_64 DMG/ZIP**이 기본이다. 유료 Apple Developer 계정, Developer ID 인증서, 공증을 릴리스 필수 조건으로 만들지 않는다. 일부 Apple 자격 증명만 구성된 경우에는 실패 처리한다. Linux는 현재 소스/빌드/CI 검증 범위이며 별도 릴리스 설치 자산은 없다.

## 2. 현재 기준과 이미 완료된 범위

## 3. 실제 제공 덤프와 운영 데이터의 경계

- 제공된 덤프는 **226개 테이블, 8,937,334행, 8개 뷰**다. 정확한 복사본에서 FK 304개 중 제약 하나의 고아 참조 11개가 발견되어 안전 전환이 올바르게 차단되었다.
- **별도 시험용 복사본에서만** 그 11행을 제외한 226개 테이블·8,937,323행의 성공 리허설을 수행했다. 원본 백업 8,937,334행을 보존했고 활성/백업 테이블 452개의 실제 `COUNT`, 뷰 8개, FK 304개를 각각 검증했다.
- 실제 Production, Staging 및 제공된 원본 덤프를 고치지 않았다. 운영 복구에는 권위 있는 스키마 정의와 부모·자식 데이터가 필요하다. 자동 행 삭제, FK 추정 복원, 시험용 행 제외를 운영 해결로 간주하지 않는다.
- 공개 문서·PR·로그에 실제 테이블명, 호스트, 계정, 덤프, 비밀값을 싣지 않는다. 새 DB 시험은 소유권을 확인한 폐기 가능한 격리 DB에서만 수행한다.

## 5. Opus 5.5 관리자 / 팀원 작업 분담과 충돌 방지

- **Opus 5.5 관리자:** 현재 상태 재검증, 객체 지원표와 보안 신뢰 모델 확정, 공유 endpoint/JSONL 프로토콜·세션 소유권·오류 코드 인터페이스 결정, 위험 리뷰, 병합·릴리스 판정. 공유 파일 변경 제안을 먼저 승인 가능한 계약으로 정리한다.
- **Sonnet 5.5 팀원 A:** `110` 연결 보안 조사·구현·테스트. 환경 대기 또는 A 작업 완료 후 `120` 마법사 응답성. 연결 UI와 터널 파일을 소유한다.
- **Sonnet 5.5 팀원 B:** `112` 쿼리 취소·제한시간·스트리밍·상한을 **한 담당자**가 맡는다. Core 세션과 결과 프로토콜, SQL worker의 일관성을 책임진다. 이후 결과 파일 저장을 맡을 수 있다.
- **Sonnet 5.5 팀원 C:** `111` 지원/거부 계약과 `105`·`108` 실DB 장애 검증을 먼저 맡고, 이어 `119` 백업 생명주기를 맡는다. 덤프·복원 파일과 정책 문서를 소유한다.
- `migration_core/src/adapters.rs::Endpoint`와 `src/core/db_core_facade.py::DbEndpoint`는 함께 바뀔 수 있는 공유 구조다. 여기에 `migration_core/src/protocol.rs`, JSONL 이벤트, 연결 세션 생명주기까지 축이 겹치는 변경은 Opus 5.5 관리자가 필드·오류·취소 의미·버전 호환성을 먼저 정한다. 각 공유 파일에는 한 시점에 한 소유자만 쓰고 다른 에이전트는 패치 제안이나 테스트 요구를 전달한다. 같은 파일을 병렬 수정하지 않는다.
- `db_core_client.py::request`는 전체 응답까지 `_lock`을 쥐고 `_send_locked`를 수행한다. UI 취소 버튼만 추가하면 실행 요청과 취소 요청이 경합해 서버 중단이 일어나지 않을 수 있다. 팀원 B의 프로토콜·세션 설계에 이 잠금 범위를 반드시 포함한다.
- `db_connection_worker.py`의 활성 worker 집합은 **스레드 실행 중뿐 아니라 GUI에 대기 중인 완료 신호도 포함**한다. `120`에서 이 소유권을 유지하고 native `QThread.finished` 뒤 queued completion → 연결 인수 또는 정리 → 활성 집합 제거 순서를 보존한다.
- 팀원은 다른 에이전트의 파일을 덮거나 타 작업의 미커밋 변경을 되돌리지 않는다. 작은 검증 가능한 변경과 근거를 Opus 5.5 관리자에게 제출하고, 통합 시 실제 diff를 리뷰받는다.

## 6. 최초 실행 체크리스트

1. `AGENTS.md`, `docs/current_status.md`, `docs/commercial_readiness_2026-09-28.md`, `docs/export_import_policy.md`를 읽고 이 인계서와 차이가 있는지 확인한다.
2. `git status --short`, `git rev-parse HEAD`, 브랜치·원격·보호 규칙·현재 릴리스·권한을 확인한다. 9월 29일의 기존 미커밋 두 문서를 보존한다. 이전 HEAD·CI 실행 숫자를 현재 검증이라고 재사용하지 않는다.
3. 기존 `.venv`의 상태를 확인한다. Windows Rust 도구는 `TEMP/tunnelforge-inspect-tools/{cargo,rustup}`에 로컬 설치되어 있을 수 있으므로 먼저 탐색하고 실행 경로를 확인한다. 없으면 표준 개발 환경을 준비한다.
4. 새 폐기 가능 MySQL/PostgreSQL DB, 제한 권한 계정, 인증서·SSH 시험 서버, 실제 Mac 및 공급자 접근의 준비 여부를 확인한다. 삭제된 다섯 Docker 컨테이너와 옛 내부 IP는 사용하지 않는다.
5. Opus 5.5 관리자가 `110`의 trust 정책, `112`의 요청/취소/결과 이벤트와 세션 소유권, `111`의 객체 지원 목록, `119`의 백업 소유권 조건을 짧은 계약으로 고정한다. 팀원 A/B/C에 각각 다른 파일 소유권을 배정한다.

## 8. 검증 실행 원칙

- **다음 구현 세션에서** 우선 변경 범위의 회귀 테스트를 돌린 뒤 아래 기본 명령을 실행한다. 광범위한 서식 변경을 부르는 저장소 전체 `cargo fmt`는 무조건적인 게이트로 두지 않는다. Rust 소스 변경의 서식은 변경 범위에서 확인한다. Windows 전체 빌드·frozen 앱 smoke, Linux 전체 앱 게이트, 실제 Mac 검증은 해당 변경·출시 범위에서 수행한다.

```powershell
.venv\Scripts\python.exe -m pytest -q
cargo test --manifest-path migration_core\Cargo.toml
cargo build --manifest-path migration_core\Cargo.toml --release
git diff --check
```
- 실DB 테스트는 `TF_MYSQL_*`, `TF_POSTGRES_*` 또는 별도 URL이 없으면 **성공처럼 반환하거나 `ignored`일 수 있다**. 통과 개수만으로 DB 실행을 주장하지 말고, 실행 환경·호스트의 격리 여부·테스트 로그·실제로 수행한 케이스를 기록한다. 특히 `migration_core/tests/live_roundtrip.rs`, `live_export_contract.rs`, `live_safe_restore.rs`, `live_import_policy.rs`, `live_schema_fidelity.rs`를 확인한다. 기존 컨테이너의 삭제 이후 새로 만든 시험 환경만 사용한다.
- MySQL 승격 시험은 `TF_PROMOTE_MYSQL_HOST`도 필요하다. 일부 live fixture는 CI 기준 포트·계정·비밀번호를 코드에 고정하므로 `TF_*` 환경변수만 바꿔 전체 시험에 반영된다고 가정하지 않는다. 각 fixture의 연결 설정과 실제 실행 로그를 확인한다.
- `.github/workflows/version-gate.yml`의 실제 DB 게이트는 아래 Rust 테스트 목록을 `--include-ignored --test-threads=1`로 실행한다. **연결 대상·계정·데이터베이스를 각 fixture에서 먼저 확인하고, 새 격리 DB를 구성한 뒤** 실행한다. 로컬에서는 PowerShell 배열을 사용한다. `TF_MYSQL_*`, `TF_POSTGRES_*`, `TF_PROMOTE_MYSQL_HOST`를 해당 환경에 맞게 설정하되, 값과 비밀번호를 문서·로그에 기록하지 않는다.

```powershell
$taskManifest = 'migration_core\Cargo.toml'
$taskLiveTests = @('live_roundtrip','live_dump_cross_engine','live_schema_fidelity','live_import_policy','live_foreign_key_actions','live_export_contract','live_safe_restore')
$taskTestArgs = @('test','--manifest-path',$taskManifest)
foreach ($taskTest in $taskLiveTests) { $taskTestArgs += @('--test',$taskTest) }
cargo @taskTestArgs -- --include-ignored --test-threads=1
cargo test --manifest-path $taskManifest --lib safe_promote_ -- --test-threads=1
cargo test --manifest-path $taskManifest --lib import::safe_restore_digest:: -- --include-ignored --test-threads=1
```

- Python의 실제 Export/Import 경로는 `tests/test_dump_python_live_contract.py`에 별도 opt-in이다. `TF_LIVE_DOCKER_RUNNER`가 없으면 skip된다. 이 시험은 실행 중인 Docker 컨테이너, `/workspace`에 마운트된 저장소, 그 안의 debug `tunnelforge-core`, `TF_LIVE_MYSQL_HOST`/`TF_LIVE_PG_HOST` 및 해당 암호 변수, 코드에 고정된 포트·사용자·`tf_test` DB가 필요하다. 격리 환경을 마련하고 파일의 cleanup 경로를 확인한 뒤 `.venv\Scripts\python.exe -m pytest tests/test_dump_python_live_contract.py -q`를 실행한다. 단순 전체 pytest 통과는 이 시험의 실행 증거가 아니다.
- 제한 계정 MySQL 동시 쓰기, PG 동시 쓰기, 연결 단절과 모호한 커밋, 잘못된 인증서·SSH 키, 양 엔진의 긴 SELECT·대량 결과는 해당 이슈에 대한 실증 근거가 필요하다. 사용자 제공 덤프의 고아 참조는 정상적으로 거부되는 사례로 유지한다.
- 실제 Mac 하드웨어 검증이 없으면 그 사실을 명시한다. macOS 보호 CI 통과와 실제 Mac 운영자 검증을 구분한다. Linux 빌드·CI와 Linux 릴리스 설치 자산의 존재도 구분한다.

## 9. 상태 기록, 릴리스, 최종 보고

- 각 비자명한 조사·구현·검증 세션에서 `docs/current_status.md`의 **Issue Tracker, Verification Log, Recommended Execution Order, Session Log**를 함께 맞춘다. 이슈 ID는 `TF-STATUS-###`로 유지한다. 같은 세션의 새 명령 증거 없이 `closed`로 바꾸지 않는다. 집중 수정만 끝났으면 `fixed_pending_full_verify`를 사용한다. 이전 성공 로그는 역사적 근거로 구분한다.
- 릴리스 전 현재 원격·보호 정책·실행 환경·권한을 다시 확인한다. 버전 변경은 버전 봇/`scripts/bump_version.py` 경로로 세 버전 파일과 status marker를 동기화한다. `docs/current_status.md`의 `Current shipping version`을 손으로 바꾸지 않는다.
- 변경 PR의 보호 CI가 **최종 정확한 HEAD**에서 통과하고 병합 커밋을 확인한 뒤, 승인된 `create-release-tag.yml`로 그 커밋의 변경 불가능한 annotated tag를 만든다. 태그가 정확히 해당 커밋으로 peel되는지 검증한다. 그 뒤 승인된 `release.yml`로 draft를 만들고 Windows·unsigned macOS arm64/x86_64 자산 및 모든 GitHub SHA-256 digest와 macOS sidecar 값을 실제 다운로드 자산과 대조한 다음 stable/latest로 게시한다.
- 실제 `UpdateChecker`가 이전 지원 버전에서 새 버전을 인식하는지 확인한다. 출판 행은 `python scripts/record_release.py`로 기록하고 결과를 `tests/test_current_status_docs.py`로 검증한다. 보호 PR·태그·릴리스 승인과 자산 검증이 빠졌다면 출시 완료라고 적지 않는다.
- 최종 인계 보고 형식: **기준 커밋/브랜치와 남은 미커밋 변경 → ID별 변경·현재 상태 → 실행한 명령과 결과(실DB/OS/공급자 여부 구분) → 미검증·차단 조건 → PR/CI/태그/자산·updater 증거(출시 시) → 다음 소유자와 첫 행동**. 실제 운영 데이터에 대한 조치는 별도 운영 승인·권위 있는 데이터 판단으로 남긴다.
